# Betsi Patient Flow

Multi-tenant patient flow and escalation platform for NHS emergency departments. The MVP is
informed by the operational failures documented in the Ysbyty Glan Clwyd ED inspection report
(`design/`): patients waiting unseen in corridors and waiting rooms, escalations nobody
acknowledged, and no auditable record of either.

## Running it

Requires the .NET 10 SDK and Docker.

```bash
docker compose up -d          # SQL Server on localhost:1433
dotnet run --project Betsi    # creates the control plane, provisions and licenses the dev tenants
```

Then open <http://localhost:5080/swagger>. Health is at `/health`.
In Swagger, click **Authorize** and enter a tenant ID and actor role before using "Try it out".

Two development tenants are seeded from `appsettings.Development.json` into the control-plane
database (`betsi_control`), each with a ten-year development licence from `Betsi/DevLicenses`.
Every request must name one; in Development you can do that with headers:

```bash
curl -X POST http://localhost:5080/api/v1/patients/register \
  -H 'Content-Type: application/json' \
  -H 'X-Betsi-Tenant: 11111111-1111-1111-1111-111111111111' \
  -H 'X-Betsi-Actor-Role: Nurse' \
  -d '{"firstName":"Gwen","lastName":"Jones","dateOfBirth":"1962-04-19"}'
```

Header-supplied tenants are a development convenience and the application **refuses to start**
with them enabled outside Development. Authentication proper arrives in Phase G.

## Escalation policy

A site has **no automatic waiting-time escalation until it approves a policy** — thresholds are
a local clinical decision, not a software default. Propose one and have a second, supervisory
user approve it: [`docs/runbooks/escalation-policy.md`](docs/runbooks/escalation-policy.md). The
board at `GET /api/v1/escalations/board` shows whether a policy is in force.

## Operating tenants

Tenants are provisioned, suspended, migrated and licensed with operator commands on the service
binary. See [`docs/runbooks/tenant-operations.md`](docs/runbooks/tenant-operations.md).

```bash
dotnet run --project Betsi -- tenants list
dotnet run --project Betsi -- license status
```

Licences are signed with `tools/Betsi.LicenseTool`. The development signing key's public half is
in `appsettings.Development.json`; its private half is not committed. To issue development
licences of your own, generate a new `dev-` key pair with `keygen` and swap the public key in.

## Tests

```bash
dotnet test Betsi.slnx
```

The domain, control-plane, licensing, repository and API suites run in-process against SQLite
and need nothing installed. The SQL Server suites (tenant migrations and end-to-end
provisioning) use Testcontainers; they skip when no Docker daemon is reachable and run in CI.

EF Core tooling is a repo-local tool: `dotnet tool restore`, then `dotnet dotnet-ef …`. There are
two contexts, so pass `--context BetsiDbContext` or `--context ControlPlaneDbContext`.

## Repository layout

| Path | Contents |
|---|---|
| `Betsi/Domain` | Aggregates, domain events, domain exceptions. No infrastructure dependencies. |
| `Betsi/Application` | Commands, validators, handlers, MediatR pipeline behaviours, escalation monitor and board queries. |
| `Betsi/Infrastructure` | EF Core persistence, tenancy, outbox. |
| `Betsi/ControlPlane` | Tenant registry, provisioning and migration, operator CLI. |
| `Betsi/Licensing` | Licence format, offline validator, feature gates. Public keys only. |
| `Betsi/API` | Controllers and the RFC 9457 problem-details handler. |
| `tests/Betsi.Tests` | Domain, infrastructure, control-plane, licensing and API tests. |
| `tools/Betsi.LicenseTool` | Licence key generation and signing. Never deployed. |
| `docs/runbooks` | Operator and site-administrator procedures. |
| `design/` | Specification and inspection-report traceability. |
| `docs/` | Architecture and API reference. |

## Conventions

- **Definition of done is "merged with tests passing in CI"**, not "it compiles". An earlier
  iteration of this project marked work complete on a successful build; most of it did not
  run. See `IMPLEMENTATION_PLAN.md` §1.
- Warnings are errors, including vulnerable and mis-constrained packages.
- Migrations are generated by `dotnet ef`, never hand-written. CI fails on model drift.
- Package versions are centralised in `Directory.Packages.props`.
