### Blocking defects found in the existing code

These must be fixed before any new feature work; several are latent runtime crashes, one is
a patient-data confidentiality risk.

- **D-1 — Infrastructure is never registered.** `InfrastructureModule.AddInfrastructure` has
  zero call sites. Every handler dependency (`IAggregateRepository<T>`, `ITenantContext`) is
  unresolvable. First call to `POST /api/v1/patients/register` fails in DI.
- **D-2 — `ITenantContext` has no registration.** The interface and `TenantContext` class are
  declared in `InfrastructureModule.cs` but never added to the container, so the DbContext
  options factory (`provider.GetRequiredService<ITenantContext>()`) throws.
- **D-3 — `AggregateRepository<T>` is not constructible by DI.** Its constructor is
  `(BetsiDbContext context, Guid tenantId)`. The container cannot supply a bare `Guid`.
- **D-4 — Self-referential DI registrations.** `InfrastructureModule.cs:30-39` registers
  `IAggregateRepository<PatientEpisode>` with a factory that calls
  `sp.GetRequiredService<IAggregateRepository<PatientEpisode>>()` — infinite recursion /
  stack overflow. Same for the other three aggregates. These four lines should be deleted;
  the open-generic registration above them already covers all cases.
- **D-5 — Tenant isolation is broken and unsafe.** Query filters close over the instance
  field `_tenantId` (`BetsiDbContext.cs:55-61`). EF caches the built model per
  `DbContextOptions`, so **the first tenant resolved in the process has its ID baked into the
  compiled model for the lifetime of the process** — subsequent tenants either see tenant #1's
  rows or see nothing. `SetTenant()` is an empty method body with a comment admitting it does
  nothing. This is a cross-tenant PII leak in a clinical system, not a cosmetic bug.
- **D-6 — Query filters are the wrong mechanism for this architecture anyway.** ADR-001
  specifies **database-per-tenant**. Isolation belongs at connection-string selection, not in
  a `WHERE TenantId = @p` predicate. The current design mixes both and implements neither.
- **D-7 — `Queue.Patients` cannot be mapped.** It is `IReadOnlyList<Guid>` configured as
  `nvarchar(max)` with no value converter (`BetsiDbContext.cs:140-142`). EF model validation
  will throw the first time the context is used. The status doc's "stored as JSON in DB" was
  never implemented.
- **D-8 — Optimistic concurrency is not enforced.** `Version` is not marked
  `IsConcurrencyToken()`. Handlers compare `episode.Version != request.ExpectedVersion` in
  memory after loading, which two concurrent writers both pass. No `DbUpdateConcurrencyException`
  can ever be raised.
- **D-9 — Version numbering is incoherent.** `AggregateRoot.MarkAsCommitted()` increments
  `Version` by exactly 1 per save regardless of how many events were raised, and
  `RaiseDomainEvent` stamps the *pre-increment* version. N events saved together all carry the
  same version number, so the event log cannot be ordered or replayed per aggregate.
- **D-10 — Package manifest is unsound.** EF Core **9.0.0** on `net10.0`;
  `MediatR.Extensions.Microsoft.DependencyInjection` 11.1.0 pinned against MediatR 12.1.1
  (NU1608 — and the package is obsolete, MediatR 12 has DI built in); Swashbuckle 6.0.0 has a
  published advisory (NU1902); a redundant `Microsoft.AspNetCore.Mvc.Core` reference (NU1510);
  and **xunit + Microsoft.NET.Test.Sdk are referenced by the web project**, which is the source
  of the CS7022 entry-point warning. There is no test project.
- **D-11 — Zero tests exist.** No test project, no test file, no assertion has ever run.

### Open decisions that gate the plan
| # | Decision | Recommendation |
|---|---|---|
| 1 | SQL Server vs PostgreSQL (flagged "**YES** blocker" in status doc) | **SQL Server.** Every artefact already assumes it (`GETUTCDATE()`, `nvarchar(max)`, `[bracket]` index filters). Switching costs ~2 days of rework for no MVP benefit. Revisit for hosting economics before Phase 1. |

## 2. Plan

Nine phases. **A, B and C are strictly sequential and must land before any feature work** —
they turn a codebase that compiles into a codebase that runs and is verifiable. D onwards
map onto the existing MVP issue numbering.

Estimates are engineer-days for one developer familiar with .NET/EF/DDD.

---

### Phase A — Make the foundation executable  ·  ~5 days  ·  **blocks everything**

Goal: `dotnet run`, migrations apply to a real database, one request round-trips end to end.

- **A-1 · Fix the package manifest** (0.5d) — D-10.
  EF Core 9.0.0 → 10.x. Drop `MediatR.Extensions.Microsoft.DependencyInjection` (MediatR 12
  self-registers). Drop `Microsoft.AspNetCore.Mvc.Core`. Swashbuckle → 7.x (or switch to the
  built-in `Microsoft.AspNetCore.OpenApi`, which is the .NET 10 default). Move xunit /
  Test.Sdk / FluentAssertions out of `Betsi.csproj`. Add `Directory.Packages.props` for
  central version management. Target: build clean with **0 warnings**, and add
  `<TreatWarningsAsErrors>` for NU1608/NU1902 so this cannot regress.
- **A-2 · Rebuild the DI graph** (1d) — D-1, D-2, D-3, D-4.
  Delete the four self-referential registrations. Give `AggregateRepository<T>` a constructor
  of `(BetsiDbContext, ITenantContext)`. Register `ITenantContext` as scoped. Call
  `AddInfrastructure` from `Program.cs`. Add a **DI-graph smoke test** that builds the root
  provider and resolves every registered service — this single test would have caught D-1
  through D-4 and must be in place before the phase closes.
- **A-3 · Implement tenant resolution properly** (1.5d) — D-5, D-6, MVP-007.
  Commit to database-per-tenant: an `ITenantConnectionResolver` maps tenant → connection
  string, and the DbContext is constructed per-request against the resolved connection.
  Delete the broken global query filters and the no-op `SetTenant()`. Keep the `TenantId`
  column as defence-in-depth and assert it on write. Add `TenantResolutionMiddleware` that
  populates `TenantContext` from the authenticated principal (header-based for now, claims
  once Phase G lands) and **rejects any request with no resolvable tenant** — fail closed.
  Add a test proving tenant B cannot read tenant A's rows.
- **A-4 · Fix aggregate versioning and concurrency** (0.5d) — D-8, D-9.
  `Version` becomes an EF concurrency token. Aggregates increment `Version` per event raised,
  and the event carries its own post-increment version. Repository stops owning version
  arithmetic. Handlers surface `DbUpdateConcurrencyException` as HTTP 409.
- **A-5 · Fix `Queue.Patients` mapping** (0.5d) — D-7.
  Value converter + `ValueComparer` to JSON, mapped over the backing field `_patients`.
- **A-6 · Regenerate migrations from the model** (0.5d) — D-11 precursor.
  **Delete the hand-written migration and snapshot.** Run `dotnet ef migrations add
  InitialCreate` so the snapshot is machine-generated and provably matches the model. Add a
  CI check (`dotnet ef migrations has-pending-model-changes`) so hand-drift cannot recur.
- **A-7 · Prove it runs** (0.5d).
  `docker-compose.yml` with SQL Server. Wire health checks (`/health` incl. DbContext probe)
  and `DatabaseInitializer` into `Program.cs`. Manual verification: app boots, migration
  applies, `POST /patients/register` returns 200 and a row lands in `PatientEpisodes`,
  `DomainEvents` and `OutboxMessages`.

**Exit criteria**: clean build, app starts, migrations apply to SQL Server in Docker, register
+ begin-triage round-trip verified against a real database, DI smoke test green.

### Phase B — Complete the write path  ·  ~6 days  ·  MVP-006, MVP-010

- **B-1 · The nine missing command handlers** (2.5d).
  `CompletePatientTriage`, `BeginPatientTreatment`, `DischargePatient`, `CancelPatient`,
  `CreateLocation`, `CreateQueue`, `EnqueuePatient`, `TriggerWaitingTimeEscalation`,
  `AcknowledgeEscalation`, `ResolveEscalation`. Each with a FluentValidation validator.
  Removes the six endpoints that currently 500.
- **B-2 · MediatR pipeline behaviours** (1d).
  `ValidationBehaviour` (makes the existing validators actually run — D's "validators exist
  but never execute"), `LoggingBehaviour`, `TransactionBehaviour`. Register validators with
  `AddValidatorsFromAssembly`.
- **B-3 · Audit logging behaviour** (1d) — MVP-010.
  An `AuditBehaviour` that writes an `AuditLogRecord` for every command — actor, role, action,
  affected aggregate, outcome, error — inside the same transaction. This is the DSPT/DCB0129
  evidence trail; the table exists today but nothing writes to it.
- **B-4 · RFC 9457 problem details** (0.5d).
  Replace the `if (result.Success) Ok() else BadRequest()` pattern with typed problem
  responses: 400 validation, 404 not found, 409 concurrency, 422 invalid state transition.
  The spec calls for RFC 9457 explicitly (MVP-065).
- **B-5 · Outbox consumer** (1d) — MVP-005 completion.
  `BackgroundService` that polls unprocessed outbox rows per tenant, dispatches, marks
  `ProcessedAt`, with retry/backoff and a poison-message cap. Without this the outbox is a
  write-only table.

**Exit criteria**: all 8 (soon ~14) endpoints return correct status codes; every command
writes an audit row; outbox drains.

### Phase C — Testing and CI  ·  ~6 days  ·  MVP-100 pulled forward

Deliberately placed **before** feature work. The project has 3,149 lines of untested code and
a status doc that mistook "compiles" for "works"; that failure mode does not self-correct.

- **C-1 · `Betsi.Tests` project + domain unit tests** (2d).
  Every state-machine transition and every illegal transition, per aggregate. Event emission
  and versioning assertions. Escalation manual-follow-up workflow.
- **C-2 · Handler + repository tests** (1.5d).
  SQLite in-memory or SQL Server Testcontainers. Transactional consistency: aggregate + event
  + outbox all commit or all roll back. Concurrency conflict raises 409.
- **C-3 · API integration tests** (1.5d).
  `WebApplicationFactory` + Testcontainers SQL Server. Full patient journey: register →
  triage → treat → discharge. Tenant isolation test from A-3 promoted here.
- **C-4 · CI pipeline** (1d) — MVP-101.
  `.github/workflows/ci.yml`: restore, build warnings-as-errors, test with coverage gate,
  `has-pending-model-changes`, `dotnet list package --vulnerable`. Branch protection on `main`.

**Exit criteria**: green CI on every PR; ≥70% line coverage on Domain and Application;
migration-drift and vulnerable-package checks enforced.

---

### Phase D — Multi-tenancy & licensing  ·  ~5 days  ·  MVP-007, 008, 009
Tenant registry and provisioning workflow; per-tenant migration runner (apply schema across N
databases); offline licence key validator with signed payload, grace period and fail-safe
behaviour; tenant onboarding runbook. A-3 delivers the request-path half of MVP-007; this
phase delivers the operational half.

### Phase E — Escalation engine  ·  ~6 days  ·  MVP-020–025
Configurable thresholds per site (4h/6h/8h); background evaluator generating escalations
automatically; manual-follow-up exception workflow for missed acknowledgement deadlines;
escalation read model and visibility dashboard API; full status-transition audit trail. This
is the single most direct answer to the ED inspection findings — it is the reason the product
exists, and it should be the first *feature* phase.

### Phase F — Clinical safety features  ·  ~10 days  ·  MVP-030–045
Age-based routing; paediatric vital-sign ranges; safeguarding flag aggregate and escalation;
trained-staff assignment; unaccompanied-child alerts; structured observations (SBAR/NEWS);
pain assessment incl. FACES/FLACC; manual deterioration flagging.
**Gate**: do not start without the named clinical safety officer from open decision #3 and a
DCB0129 hazard log. Shipping paediatric triage logic without clinical sign-off is not
acceptable regardless of schedule pressure.

### Phase G — API, auth, integration  ·  ~8 days  ·  MVP-060–070
OAuth2/OIDC (NHS CIS2 where applicable); role-based authorisation on every endpoint — note
**there is currently no authentication of any kind**; API versioning; webhook delivery off the
outbox; HL7/FHIR adapter; OpenAPI publication.

### Phase H — UI & dashboards  ·  ~15 days  ·  MVP-080–095
Query/read-model side first (there is none today — the system is write-only), then waiting
room board, escalation dashboard, triage scoreboard, discharge tracking, workspace editor,
site configuration UI. Real-time transport (SignalR) decision needed before start.

### Phase I — Deployment & operations  ·  ~7 days  ·  MVP-102–115
CD pipeline, staging/production environments, monitoring and alerting, backup/restore drill,
operator runbooks, DSPT evidence pack.

## 3. Sequencing

```
A ──▶ B ──▶ C ──┬──▶ D ──┬──▶ E ──▶ F ──▶ H
                │        │
                └──▶ G ──┘        (G can run parallel to E once C lands)
                                   I trails E/G
```

**Critical path to a pilot-ready MVP**: A → B → C → D → E → G → H → I ≈ **58 engineer-days**,
plus Phase F (10d) gated on clinical governance. With one developer that is roughly 12–14
weeks, not the "30 days" in `.github/project.md`. That estimate should be revised with
stakeholders before Phase 0 sign-off.
